# Prompt part — migrate a consumer from Enigma.Core 1.1.0 to 2.0.0

*Reusable block. Paste into a prompt for any repository that references `Enigma.Core` 1.x.*

---

## Task

Upgrade this repository's `Enigma.Core` package reference from **1.1.0 to 2.0.0** and update every call
site the major release breaks. This is an **API migration, not a crypto review**: do not change key
sizes, hash choices, padding modes, signature algorithms, or certificate policy while migrating. Do not
add compatibility wrappers that re-create the 1.x shape — adopt the new shape.

## What breaks — and this is the only thing that breaks

2.0.0 has exactly one breaking theme: **RSA key material no longer crosses the public surface as PEM
text.** A key is parsed once into an `RsaKey` handle (`Enigma.Core.Asymmetric.PublicKey.RsaKey`), and
that handle is passed to every RSA and certificate operation. The per-call `char[]? password` parameters
are gone with it — a passphrase is supplied once, where the key is parsed.

Removed members were **deleted outright**. Nothing is `[Obsolete]`, there are no shims and no
transitional overloads, so 1.x call sites **fail to compile rather than warn**. That is the detection
mechanism for this migration: **the build error list is the to-do list.** Work it to zero.

Everything else in 2.0.0 is additive. Block/stream ciphers, padding, hashing, HMAC, key derivation,
encoding, OTP, the ML-KEM/ML-DSA operation services, and every certificate member that does not take a
key are **untouched** — leave that code alone.

## Step 1 — bump the reference

Set the `Enigma.Core` version to `2.0.0` (in `Directory.Packages.props` if the repo uses Central Package
Management, otherwise on each `<PackageReference>`), restore, then build to enumerate the breaks.

Compatibility, so you know what you do *not* have to touch:

- Target frameworks unchanged: `netstandard2.0`, `net8.0`, `net10.0`.
- `BouncyCastle.Cryptography` floor unchanged at **2.7.0** (that move happened in 1.1.0).
- No new transitive dependency; the new Checksum module is implemented in-repo.

## Step 2 — RSA: `IPublicKeyService`

Every member changed. Mechanical mapping:

| 1.x (removed) | 2.0.0 (replacement) |
|---|---|
| `(string, string) GenerateRsaKeyPair(int, char[]?)` | `RsaKey GenerateRsaKey(int)` + `RsaKey.ExportPublicKeyPem()` / `ExportPrivateKeyPem(char[]?)` |
| `EncryptPkcs1(byte[], string)` | `EncryptPkcs1(byte[], RsaKey)` |
| `DecryptPkcs1(byte[], string, char[]?)` | `DecryptPkcs1(byte[], RsaKey)` |
| `EncryptOaep(byte[], string, RsaOaepHash)` | `EncryptOaep(byte[], RsaKey, RsaOaepHash)` |
| `DecryptOaep(byte[], string, RsaOaepHash, char[]?)` | `DecryptOaep(byte[], RsaKey, RsaOaepHash)` |
| `Sign(byte[], string, RsaSignatureAlgorithm, char[]?)` | `Sign(byte[], RsaKey, RsaSignatureAlgorithm)` |
| `Verify(byte[], byte[], string, RsaSignatureAlgorithm)` | `Verify(byte[], byte[], RsaKey, RsaSignatureAlgorithm)` |

The 2.0.0 surface in full:

```csharp
// Enigma.Core.Asymmetric.PublicKey
RsaKey GenerateRsaKey(int keySizeBits = 2048);
byte[] EncryptPkcs1(byte[] data, RsaKey key);
byte[] DecryptPkcs1(byte[] ciphertext, RsaKey key);
byte[] EncryptOaep(byte[] data, RsaKey key, RsaOaepHash hash = RsaOaepHash.Sha256);
byte[] DecryptOaep(byte[] ciphertext, RsaKey key, RsaOaepHash hash = RsaOaepHash.Sha256);
byte[] Sign(byte[] data, RsaKey key, RsaSignatureAlgorithm algorithm = RsaSignatureAlgorithm.Sha256WithRsa);
bool   Verify(byte[] data, byte[] signature, RsaKey key, RsaSignatureAlgorithm algorithm = RsaSignatureAlgorithm.Sha256WithRsa);
```

```csharp
// Enigma.Core.Asymmetric.PublicKey.RsaKey
int  KeySizeBits   { get; }   // modulus size, e.g. 2048
bool HasPrivateKey { get; }   // false for a public-only handle

static RsaKey ImportPublicKeyPem(string pem);
static RsaKey ImportPrivateKeyPem(string pem, char[]? password = null);

string ExportPublicKeyPem();                          // SubjectPublicKeyInfo "PUBLIC KEY"
string ExportPrivateKeyPem(char[]? password = null);  // PKCS#8; PBES2 when a password is given
```

`GenerateRsaKeyPair` → `GenerateRsaKey` is a **rename, not just a retype**: one handle carries both
halves, so "key pair" no longer described the return value. Code that destructured the old tuple into
two PEM strings should keep the handle instead and export a PEM only where a PEM is genuinely needed (a
file, a wire format, a database column).

`RsaOaepHash` lives in `Enigma.Core.Asymmetric.PublicKey`; `RsaSignatureAlgorithm` lives in
`Enigma.Core`. Both are unchanged, and both still default to their SHA-256 variant.

## Step 3 — certificates: `IX509CertificateService`

| 1.x | 2.0.0 |
|---|---|
| `GenerateSelfSignedCertificate(string, string privateKeyPem, DateTimeOffset, DateTimeOffset, RsaSignatureAlgorithm, char[]? password, X509CertificateOptions?)` | `GenerateSelfSignedCertificate(string, RsaKey privateKey, DateTimeOffset, DateTimeOffset, RsaSignatureAlgorithm, X509CertificateOptions?)` |
| `GenerateCertificateSigningRequest(string, string privateKeyPem, RsaSignatureAlgorithm, char[]? password)` | `GenerateCertificateSigningRequest(string, RsaKey privateKey, RsaSignatureAlgorithm)` |
| `IssueCertificate(string, string, string issuerPrivateKeyPem, DateTimeOffset, DateTimeOffset, RsaSignatureAlgorithm, char[]? password, X509CertificateOptions?)` | `IssueCertificate(string, string, RsaKey issuerPrivateKey, DateTimeOffset, DateTimeOffset, RsaSignatureAlgorithm, X509CertificateOptions?)` |
| `ExportPkcs12(string, string privateKeyPem, char[] password, IReadOnlyList<string>?)` | `ExportPkcs12(string, RsaKey privateKey, char[] password, IReadOnlyList<string>?)` |
| `(string certificatePem, string privateKeyPem) ImportPkcs12(byte[], char[])` | `(string certificatePem, RsaKey privateKey) ImportPkcs12(byte[], char[])` |

Unchanged on that service — do not touch these: `IsCertificateSigningRequestValid`, `ValidateChain`,
`IsRevoked`, `GetCertificateInfo`, `ExportCertificateToDer`, `ImportCertificateFromDer`,
`CertificateInfo`, `X509CertificateOptions`, `X509KeyUsage`, `IX509CertificateServiceFactory`.
Certificates, CSRs and CRLs still cross the API as **PEM strings** — only *private keys* became handles.

Two traps here:

- **The `char[] password` on `ExportPkcs12` / `ImportPkcs12` stays.** It protects the PKCS#12 archive,
  not a key PEM. Do not delete it while removing the other password parameters.
- **Shifted positional arguments.** `char[]? password` sat between `signatureAlgorithm` and `options`.
  With it gone, an `options` argument passed positionally now binds to the wrong parameter. Usually that
  is a compile error — but audit every call site that did **not** use `options:` and confirm the options
  object still lands on `options`.

`ImportPkcs12` now hands back a usable handle, so drop any re-import that followed it:

```csharp
// 1.x — the returned PEM had to be re-parsed before use
(string certPem, string keyPem) = certificates.ImportPkcs12(pfx, pfxPassword);
RsaKey key = RsaKey.ImportPrivateKeyPem(keyPem);

// 2.0.0 — the handle *is* the return value
(string certPem, RsaKey key) = certificates.ImportPkcs12(pfx, pfxPassword);
```

If a code path genuinely needs that key as a file, call `key.ExportPrivateKeyPem(password)`. Note the
1.x return was always **unencrypted**, so code that wrote it straight to disk was writing a bare private
key; passing a password to the export is the better choice now that it is available. A PKCS#12 whose key
entry is not an RSA key now throws `ArgumentException` (there is no `RsaKey` to return).

## Step 4 — the passphrase moves to the import

No member of `IPublicKeyService` or `IX509CertificateService` takes a passphrase any more. Supply it
once to `RsaKey.ImportPrivateKeyPem` and reuse the handle.

```csharp
// 1.x — the passphrase travelled with every private-key call
byte[] signature = rsa.Sign(message, privateKeyPem, RsaSignatureAlgorithm.Sha256WithRsa, password);
byte[] recovered = rsa.DecryptOaep(ciphertext, privateKeyPem, RsaOaepHash.Sha256, password);
bool   valid     = rsa.Verify(message, signature, publicKeyPem);

// 2.0.0 — supplied once, where the key is parsed
RsaKey key = RsaKey.ImportPrivateKeyPem(privateKeyPem, password);
byte[] signature = rsa.Sign(message, key, RsaSignatureAlgorithm.Sha256WithRsa);
byte[] recovered = rsa.DecryptOaep(ciphertext, key, RsaOaepHash.Sha256);
bool   valid     = rsa.Verify(message, signature, key);   // the private handle verifies too
```

An encrypted CA key used to mean repeating the passphrase at every certificate call site; now the handle
does the rest:

```csharp
// 2.0.0
RsaKey caKey = RsaKey.ImportPrivateKeyPem(caPrivateKeyPem, password);

string caCertPem = certificates.GenerateSelfSignedCertificate(
    "CN=Example Root CA", caKey, notBefore, notAfter,
    RsaSignatureAlgorithm.Sha256WithRsa, caOptions);

string csrPem = certificates.GenerateCertificateSigningRequest("CN=service.example.com", caKey);

string leafPem = certificates.IssueCertificate(
    csrPem, caCertPem, caKey, notBefore, notAfter,
    RsaSignatureAlgorithm.Sha256WithRsa, leafOptions);
```

## Step 5 — move the exception handling with it

**A wrong or missing passphrase now surfaces from `RsaKey.ImportPrivateKeyPem`, not from the operation
that used to consume it.** Any `try`/`catch` that wrapped `Sign` / `Decrypt*` / a certificate call to
report "bad password" must move to the import. This is a silent behaviour change — the compiler will not
find it. Grep for the catch sites deliberately.

Exception contract of the new surface:

| Condition | Exception |
|---|---|
| Malformed PEM, or a PEM holding the wrong kind of key | `ArgumentException` |
| Encrypted PEM with a wrong or missing passphrase | `CryptographicException` (`System.Security.Cryptography`) |
| Public-only handle passed to `Sign`, `DecryptPkcs1`, `DecryptOaep`, or any certificate signing / `ExportPkcs12` call | `ArgumentException` |
| `ExportPrivateKeyPem()` on a public-only handle | `InvalidOperationException` |
| PKCS#12 whose key entry is not RSA | `ArgumentException` |

## `RsaKey` semantics to rely on when refactoring

- **Immutable and thread-safe.** A handle carries the key it was built from and nothing else. Cache it
  in a field, a singleton, or a DI-registered holder, and use it concurrently from several threads.
- **A private handle also serves the public operations** — `Verify`, `EncryptPkcs1` and `EncryptOaep`
  derive the public half internally. Code that kept a public-key PEM around purely to verify its own
  signatures can drop it.
- **Deliberately not `IDisposable`.** BouncyCastle holds private components as arbitrary-precision
  integers — immutable managed objects the GC may copy — so there is no address a `Dispose` could
  reliably overwrite. Do not add a `using`, and do not write a wrapper that pretends to wipe it. Treat
  the lifetime of a private handle as the lifetime of the secret and keep it as short as the app allows.
- **The caller owns the passphrase array.** The library uses `char[]` in place and never clears it.
  Clear it yourself after the import if that is your policy.
- Use `HasPrivateKey` to branch instead of catching, and `KeySizeBits` where you previously re-parsed a
  PEM to learn the modulus size.

## Refactor the shape, not just the signatures

The point of the release is to stop re-parsing. A migration that imports a handle immediately before
each call compiles but throws away the entire benefit. So:

- **Import once per key, per lifetime.** Hoist `ImportPrivateKeyPem` out of loops, per-request paths,
  and helper methods that take a PEM string parameter.
- **Stop storing PEM strings as the in-memory representation.** Fields, records, DTOs and options
  classes that carried `string PrivateKeyPem` in order to pass it to Enigma.Core should carry `RsaKey`.
  Keep PEM only at the boundaries — file, config, network, database.
- **Push the handle into DI / composition.** A signing service that received a PEM string and a password
  per call should receive an `RsaKey` (or a small provider of one) at construction.
- Why it matters: for a 2048-bit key, roughly **84 %** of a 1.x `Sign(data, encryptedPem, password)`
  call was key reconstruction — BouncyCastle validates the CRT components on construction.

## Key files and stored data: nothing to migrate

**Only the API broke, not the file formats.** Every key PEM written by 1.x still imports.

- `ImportPrivateKeyPem` reads all three forms: unencrypted PKCS#8 (`PRIVATE KEY`), PBES2-encrypted
  PKCS#8 (`ENCRYPTED PRIVATE KEY`), and the traditional OpenSSL envelope (`RSA PRIVATE KEY`, with or
  without `Proc-Type` / `DEK-Info`).
- `ExportPrivateKeyPem(password)` now **writes** PBES2 (PBKDF2-HMAC-SHA256, AES-256-CBC, 16-byte salt,
  600 000 iterations) instead of the legacy OpenSSL envelope (whose derivation was `EVP_BytesToKey` —
  MD5, one iteration). File-compatible in both directions: 1.x reads PBES2 too, so a key written by
  2.0.0 can still be loaded by a 1.x consumer during a staged rollout.
- Budget for it: **~0.6 s per encrypted key at import**, paid once per handle rather than once per
  operation. If a hot path previously absorbed cheap-but-repeated legacy imports, move the import to
  startup or a cache. Do not weaken the derivation to claw that 0.6 s back.
- No stored key needs converting. To move one onto the stronger derivation, import it and export it
  again.
- ML-KEM / ML-DSA raw key, ciphertext and signature encodings are unchanged; persisted PQC material
  keeps working.

## Optional, additive — adopt only if it removes code here

Do not chase these during the migration; note them and raise them separately if this repo hand-rolls the
equivalent.

- **PQC key PEM services** — `IMLDsaPemService` / `IMLKemPemService` (+ their factories) in
  `Enigma.Core.Asymmetric.Pqc`: `GenerateKeyPairPem`, `ToPublicKeyPem` / `ToPrivateKeyPem`,
  `FromPublicKeyPem` / `FromPrivateKeyPem` (which recover the parameter set from the algorithm OID in
  the PEM). Private-key format is selectable via `MLPrivateKeyPemFormat` (`Seed`, `ExpandedKey`,
  `SeedAndExpandedKey`); encrypted keys use the same PBES2 scheme as RSA. `IMLDsaService` and
  `IMLKemService` are unchanged.
- **Checksum module** — `Enigma.Core.Checksum`: `IChecksumService` / `IChecksumServiceFactory` over
  seven CRC variants (CRC-16 ARC, CCITT-FALSE, XMODEM, MODBUS, KERMIT; CRC-32 ISO-HDLC, CRC-32C). One
  factory method per variant, `byte[]` or `Stream`, sync or async with `IProgress<int>` and a
  `CancellationToken`. **A CRC is error detection, not a security primitive** — never swap a hash or
  HMAC for one.

## Find the call sites

```bash
# every Enigma.Core RSA / certificate touchpoint
grep -rn --include='*.cs' -E 'IPublicKeyService|PublicKeyServiceFactory|IX509CertificateService|X509CertificateServiceFactory'

# 1.x members that no longer exist in this form
grep -rn --include='*.cs' -E 'GenerateRsaKeyPair|EncryptPkcs1|DecryptPkcs1|EncryptOaep|DecryptOaep|GenerateSelfSignedCertificate|GenerateCertificateSigningRequest|IssueCertificate|ExportPkcs12|ImportPkcs12'

# PEM strings and passphrases held for the purpose of passing them in
grep -rn --include='*.cs' -iE 'privateKeyPem|publicKeyPem|keyPem|PrivateKeyPassword|KeyPassphrase'

# catch sites that must move to the import (Step 5)
grep -rn --include='*.cs' -B4 -E 'catch \((CryptographicException|Exception)' | grep -iE 'sign|decrypt|certificate|pkcs12'
```

## Definition of done

1. `Enigma.Core` reference is `2.0.0`; restore is clean.
2. Solution builds with **zero warnings and zero errors** on every target framework (do not silence a
   warning to get there).
3. Full test suite green. Tests that constructed keys as PEM strings were updated to handles — not
   deleted, not skipped.
4. No `RsaKey.Import*` call sits inside a loop or a per-request path that could be hoisted; no field or
   DTO still carries a private-key PEM purely to feed Enigma.Core.
5. Every `options` argument to `GenerateSelfSignedCertificate` / `IssueCertificate` verified to bind to
   `options` (the Step 3 trap).
6. Bad-passphrase handling now sits at the import (Step 5), verified by reading the catch sites — not
   inferred from the build passing.
7. No wrapper, extension method, or helper was added to re-create the removed PEM-string overloads.
8. Round-trip verified against **real existing key material**: a key file written by the 1.x code path
   still imports and still signs/decrypts as before.
